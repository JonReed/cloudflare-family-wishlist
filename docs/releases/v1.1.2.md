# Family Wishlist v1.1.2

Clearer gift status, compact wish titles and guest reservations through existing sharing links.
This patch includes the accumulated improvements since v1.1.1, prepared on 16 October 2026.

## What's changed

- Bought gifts have a pale green row and a **✓ Bought** label in the signed-in family view. The
  recipient's signed-in view continues to receive no reservation or purchase information.
- Shared lists clearly mark unavailable gifts with a pale green row and **✓ Reserved**. Only the
  guest managing their own purchase sees **✓ Bought**; other visitors see reservation availability.
- Long wish titles fold to two lines, with **Show full title** and **Show less** when needed, on
  family and shared lists. Saved titles stay complete. Without JavaScript, they appear in full.
- Guests can reserve gifts through every existing or new sharing link, mark their own gifts bought,
  release them and recover reservations on another device with a private code. First use confirms
  that the browser can save the required cookie before creating a reservation. Requests have shared
  and per-guest limits, and concurrent reservations cannot double-book a gift.
- Cookie and picture privacy information appears throughout the app. Viewing a shared list alone
  does not create a guest reservation cookie.
- Product pictures load directly from validated HTTPS shop addresses, avoiding Worker image-proxy
  requests. Failed pictures leave the wish usable. Picture hosts receive the browser request and may
  use their own cookies; requests omit the wishlist address, sharing code and sign-in details.
- Household setup commands accept explicit inputs for agents without an interactive terminal,
  including safeguards against reusing the wrong database.

## Updating an existing installation

Follow [Choose how to update](https://github.com/JonReed/cloudflare-family-wishlist/blob/v1.1.2/docs/UPDATES.md).
Keep your saved household settings and make a recovery point as described in that guide. Existing
web addresses, wishes, member reservations and sharing links are preserved. No new runtime secret,
Cloudflare binding or Access configuration is required for this update.

**Review your sharing links:** existing links now allow guest reservations and reveal availability
to everyone with the address, including a recipient opening it anonymously. They do not reveal who
is buying a gift or another person's purchase state. Stop any unwanted links from **Manage → Sharing
links**. Signed-in recipient privacy remains unchanged. Save guest recovery codes privately; anyone
with a code can manage its reservations.

The supported deploy command, `npm run deploy:production`, applies two pending migrations before
deploying the Worker:

- `0014_guest_claims.sql` preserves member claims while adding guest reservations and request counters.
- `0015_shared_image_list_sized_limits.sql` preserves and widens the earlier image-counter tables.
  The current app no longer uses those product-image counters; the migration remains in the ordered
  upgrade history.

A failed Worker deployment does not undo SQL already applied. Follow the update guide's recovery
steps rather than creating a replacement database. Automatic delivery remains opt-in; publishing
this release does not enable it for a household.

## Verification

Local release preparation passed `npm run quality` and `npm run audit`: 585 Workers-runtime tests,
four setup-script tests, eight updater integration tests, formatting, lint, type generation and a
production build; the audit reported zero known vulnerabilities. Upgrade tests check preservation
of earlier household data through the migrations.

Chrome QA covered desktop and narrow mobile layouts, title expansion and editing, recipient privacy,
guest purchase visibility, and reservation, confirmation, recovery and release forms with and without
JavaScript, including a local HTTPS production preview. This is local evidence, not verification of
every household's deployment. See the
[review scope and limits](https://github.com/JonReed/cloudflare-family-wishlist/blob/v1.1.2/docs/SECURITY_REVIEW.md#v112-release-preparation).

The **Release to stable** workflow reruns the required gates before promoting the exact tagged
commit. Check its result before treating publication as a successful stable update.
