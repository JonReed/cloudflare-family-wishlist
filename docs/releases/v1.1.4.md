# Family Wishlist v1.1.4

More reliable product imports and simpler sharing, with reservations remembered by the sharing link.

## What's changed

- **Manage** keeps a copyable URL for every active sharing link, including older links. Previously
  sent addresses continue to work. The stop-sharing confirmation stays in place when opened.
- Guest reservations belong to the named sharing link. Opening that link on another device shows
  the same reservations and purchases, without a guest cookie or recovery code. The family sees the
  link's name against its reservations.
- Shared pages reuse the normal gift-tag navigation and its full page width. Unnecessary introductory
  and recovery instructions have been removed.
- Browser Run handles larger product-page responses and reports more specific failures. eBay UK
  imports can extract the primary price from larger listings.
- Development dependencies have been updated to resolve dependency-audit findings.

## Updating an existing installation

1. Use your existing [update method](https://github.com/JonReed/cloudflare-family-wishlist/blob/v1.1.4/docs/UPDATES.md).
   Households with automatic updates enabled receive this release after it passes promotion to
   `stable` and their next scheduled update runs. Publishing a release does not enable automatic
   updates for households that chose manual updates.

   **Done when:** your update and Cloudflare build have succeeded and the website footer shows **1.1.4**.

2. Check your existing links in **Manage → Sharing links**. Anyone with a particular link can see and
   manage that link's reservations, including its bought status. Use separate named links for people
   who should manage separate reservations. Other links see only **Reserved**, without buyer details.
   The recipient's signed-in wishlist still receives no claim or purchase data.

   **Done when:** the active links are the ones you intend people to use.

### Automatic database migration

The existing **Deploy command**, `npm run deploy:production`, automatically applies
`0016_link_reservations.sql` before deploying the new Worker. The household updater includes that
file in the release update. No manual SQL, new secret, binding or Access change is needed for a
household using the documented deployment setup.

The migration adds a nullable sharing-link name to reservations. Existing members, wishes, sharing
links and reservations remain in place. Applied migrations are recorded and skipped on retries.
If a migration fails, the new Worker is not deployed. The previous Worker remains compatible with
the added column if a later deployment step fails. Follow the
[update recovery instructions](https://github.com/JonReed/cloudflare-family-wishlist/blob/v1.1.4/docs/UPDATES.md);
do not replace the database.

**Older guest reservations remain reserved.** Their original sharing link was not recorded, so they
cannot be automatically assigned to a named link. Old recovery codes no longer manage them. If one
needs changing, ask a family member other than the recipient to use **Clear a guest reservation**,
then reserve it again through the intended sharing link.

## Verification

Release checks cover the full quality and dependency-audit gates, including a v1.1.3 database upgrade
with existing member claims, guest reservations and purchases; safe migration retries; compatibility
with old Worker writes; and delivery of the migration file through the household updater.
Existing deployment tests confirm that a failed migration prevents Worker deployment.

The application changes were also checked in desktop and narrow mobile browsers, including matching
gift-tag layouts and reservations across separate browsers. These checks do not verify every
household's Cloudflare settings or deployment. See the
[review scope and limits](https://github.com/JonReed/cloudflare-family-wishlist/blob/v1.1.4/docs/SECURITY_REVIEW.md#v114-release-preparation).
The **Release to stable** workflow repeats the required gates before promoting the exact tagged commit.
